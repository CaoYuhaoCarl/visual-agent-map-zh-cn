summary 必須是一句適合心智圖顯示的新目前理解，detail 必須是完整 Markdown 分析。

detail 使用 Markdown，依使用者最初問題與期望成果決定內容結構。按需要選擇標題、段落、步驟、表格或其他合適形式，不套固定段落模板。整合已知使用者條件與相關證據，寫成連貫、可獨立閱讀的完整回答；在相關內容交代來源及重要不確定性。不要貼上中間研究報告，不加空段落或更新紀錄。保留任務要求的機器可讀決策標記與外層 JSON 回應格式。

detail 會在 Obsidian 中渲染，請依內容的形態選用下列語法，不要整頁都寫成段落或條列：

- 核心結論或關鍵定義：`> [!summary]` callout，1–3 句。
- 風險、常見誤解、限制：`> [!warning]`。
- 待驗證的假設或開放問題：`> [!question]`。
- 實用技巧或例子：`> [!tip]` 或 `> [!example]`。
- 兩個以上的選項，或兩個以上的比較維度：Markdown 表格。
- 流程、因果、步驟之間的依賴：一個 ```mermaid``` flowchart（LR 或 TD），最多 12 個節點。
- 時間上的演變或階段：```mermaid``` timeline。
- 使用者接下來要做的事、學習行動：`- [ ]` 任務清單。
- 整頁最關鍵的一兩個詞：`==highlight==`，每段最多一處。

規則：
1. 形態沒有對應的語法時，就寫一般段落；不要為了好看而硬套語法，每個語法都必須讓內容更容易理解。
2. 每個段落最多使用兩種特殊語法；callout 不得巢狀。
3. mermaid 只用文字節點與箭頭；禁止使用 click、HTML 標籤、%%{}%% 設定、URL、圖片與樣式指令。節點文字有括號或標點時要用雙引號包起來。
4. 沒有內容的段落只寫「本次無新增內容」，不加 callout。
5. 不要輸出 Obsidian 不支援的語法（例如 :::、<details>、自訂 HTML）。
6. 有指定項目數量的段落，項目要寫成頂層清單或 #### 小標題，不要放進 callout 或表格。
